Delivery 2A merged after its exact-head gates passed; that merge did not enable the feature or complete Work Order 2. Production enablement remains withheld under the current HOLD and 2B acceptance. Findings must never interpret `uncertain`, `unexecutable`, `not_authorized` or a missing check as a clean result.

The `/1` to `/2` profile change alters exact finding identities. This is safe for a first activation only while `/1` has never produced persisted customer findings; if that condition is false, a compatibility and retest plan is required before enabling `/2`.

The 13 October Docker lab ran each 22-test suite under a one-CPU, 512 MiB container cap with networking disabled. Each suite completed in 2.16–2.31 seconds and measured 40 checks, 43 engine connections and 92,189 TLS wire bytes. The highest coarse `docker stats` sample during the repeated build-stage test load was 16.86 MiB and 82.96% of one CPU. The final runtime image was 361,885,971 bytes and its idle sample was 804 KiB. These are local lab measurements with different process mixes; they do not establish production collector peak memory, customer-scale throughput or Cloudflare container cost.

For delivery 2B, local image inspection measured the pinned stage 1 no-zlib runtime image at 361,885,971 bytes and the final zlib-enabled runtime image at 361,915,234 bytes (+29,263 bytes). Both were built from the same pinned runtime base. This image-size comparison does not substitute for the remaining representative production-runtime CPU, memory, latency and billable-cost profile.

The reproducible 2B final-image loopback profile above uses `CM_TLS_TEST_RUNTIME_ROOT=/opt/cybermeters`, a disposable self-signed localhost certificate, `CM_TLS_TEST_PROFILE=1`, and `node /code/scripts/profile-tls-final-runtime.mjs 20` in a read-only container with `--network none --cpus 1 --memory 256m --pids-limit 64`. Its 200 results were 100 accepted, 20 rejected, 20 unknown, 20 unexecutable and 40 uncertain; the last three states remain explicit, never clean. Ten warm local Docker Desktop startups took 156.10 ms median and 491.84 ms p95 for the 2B image, versus 129.17 ms median and 258.18 ms p95 for the 2A image under the same limits. That small, noisy sample includes Docker Desktop overhead and is not a Cloudflare startup or billing measurement.

A paired 20-iteration run then used the **same candidate collector source and fixture** against the earlier 2A no-zlib final image (`CM_TLS_TEST_BASELINE_IMAGE=1`) and the 2B zlib-enabled final image. Both had 200 checks. The 2A image made 140 connections, sent 87,200 bytes, received 140,834 bytes, used 1,701,021 CPU microseconds in 1,691.46 ms wall and reached 35,106,816 bytes cgroup peak memory; its 20 compression checks were `unexecutable`. The 2B image made 160 connections, sent 98,660 bytes, received 169,856 bytes, used 1,717,716 CPU microseconds in 1,701.57 ms wall and reached 35,168,256 bytes peak; those 20 checks were `accepted` with compression absent. The 20 extra connections and wire-byte differences reflect actually measuring compression. A single short paired sample cannot establish a stable CPU/memory delta or billable Cloudflare cost; it isolates the runtime binary difference rather than comparing two deployed source versions.

Rollback guard: if `TLS_ASSESSMENT_MODE` is switched off after a job was planned, the Queue consumer now completes all remaining TLS controls as `unexecutable / feature_disabled` without a new collector call or network charge, resumes the ordinary scan, and leaves TLS quality `partial`. The synthetic queue fixture covers a plan larger than one slice. A real version rollout and any already-running old-version invocation still need controlled live rollback proof; the local guard alone does not clear the production HOLD.
