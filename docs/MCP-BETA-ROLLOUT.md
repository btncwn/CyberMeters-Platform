# CyberMeters MCP Beta rollout handoff

**State:** local engineering only. The customer gateway is disabled by default, has no public route, and cannot read customer data without the API Worker's private bindings. This document prepares a later controlled staging and named-customer rollout; it is not a deployment record.

## Release sequence

1. **Select the pilot.** Record the named workspaces, owner, support contact, supported client surfaces, and rollback operator. Check that every pilot user, including a single-domain legacy owner, has an explicit live `workspace_members` row; customer OAuth intentionally requires it. Approve the MCP audit retention and the customer notice about data handled by their chosen AI client. Keep the core product release decision independent of MCP.
2. **Prepare isolated staging.** Use the fixed `api-staging.cybermeters.com`, `app-staging.cybermeters.com`, and `mcp-staging.cybermeters.com/mcp` origins. Create and review separate staging Wrangler configurations for both Workers before any hosted test: the API route must target only the staging hostname, its D1 binding must use a dedicated staging database, its `OAUTH_KV` binding must use a dedicated namespace, and the gateway's named service bindings must target the staging API Worker. The checked-in production Wrangler files point at the production API route, D1, and service name; setting `MCP_DEPLOYMENT_TIER=staging` alone does not isolate them. Apply migration `121-mcp-oauth.sql` to the staging database and dry-run both staging configurations to verify the effective routes and bindings. Set `MCP_DEPLOYMENT_TIER=staging` in both Workers. The optional `MCP_STAGING_*` assertions, if supplied, must match the fixed staging origins exactly. Keep staging data synthetic until the tenant and privacy gates pass.
3. **Configure the client boundary.** Keep the gateway's named `MCP_AUTH` and `MCP_CUSTOMER_BACKEND` service bindings and both edge rate bindings. Put a Cloudflare edge abuse rule on the dedicated MCP hostname and the API OAuth paths, then exercise a bounded burst against staging so distributed authorization attempts cannot grow the shared API database without an operational limit. Configure exact hosted OAuth redirect URIs in `MCP_OAUTH_DCR_ALLOWED_REDIRECT_URIS` only for approved clients. A Gemini Enterprise connection needs a separate operator-provisioned confidential OAuth client; never expose its secret in this repository or enable open confidential-client registration.
4. **Enable staging in order.** Deploy API and gateway code with customer flags absent; verify the gateway returns `503 mcp_not_configured`. Enroll only the approved staging workspaces in `mcp_beta_workspace_access`. Then enable `MCP_CUSTOMER_OAUTH_ENABLED`, `MCP_CUSTOMER_READ_ENABLED`, and, where needed, `MCP_OAUTH_DCR_ENABLED` on the API Worker; enable `MCP_CUSTOMER_ENABLED` on the gateway; set `VITE_MCP_BETA_ENABLED=true` only on the staging app. Check OAuth metadata, PKCE consent, read-only tool discovery, tenant isolation, rate limiting, durable audit, revocation, account/workspace deletion fences, and an intentional audit-store outage.
5. **Prove actual clients.** Test Claude Code, Codex CLI, and Gemini CLI with the customer OAuth flow. Test Claude.ai/Desktop, a private ChatGPT MCP app, and an eligible Gemini hosted surface separately over staging HTTPS before advertising each one. Record account/region/admin eligibility and an actual read, revoke, and reconnect for every advertised surface. A local protocol simulator is not a hosted-client pass.
6. **Decide the canary.** An explicit Founder/Executive beta decision is required before a production route, flag, or customer enrollment is enabled. Canary one named workspace, watch bounded success/denial/latency metrics and audit availability, then widen only after the evidence and support owner are recorded.

## Staging configuration preparation

Put the actual dedicated staging D1 UUID, OAuth KV namespace ID, and two distinct staging rate namespace IDs in an ignored `local/mcp-staging-resources.json` file. Run `node scripts/generate-mcp-staging-config.js local/mcp-staging-resources.json`, then review the two generated `workers/{scan-api,mcp-server}/.wrangler/mcp-staging/wrangler.jsonc` files and run `node scripts/validate-mcp-staging-config.js`. Dry-run both generated configurations and check their effective bindings. The generator never deploys, enables customer flags, or accepts the production D1/rate IDs.

Provision the dedicated `cybermeters-reports-staging` R2 bucket and staging hostnames separately. Prepare the staging frontend and identity login; Microsoft SSO also needs the exact staging redirect registered in Entra. Verify the resource identities in Cloudflare before any hosted test: static IDs and local dry-runs cannot prove account ownership or actual resource isolation. The staging API intentionally has no Queue or cron binding. Its scan dispatch is fail-closed, and the test validator proves a scan request cannot execute without the Queue.

## Immediate rollback

- Disable the gateway's `MCP_CUSTOMER_ENABLED` flag or remove its public route; leave the rest of CyberMeters serving normally.
- Set `MCP_CUSTOMER_READ_ENABLED=false` on the API Worker and pause all `mcp_beta_workspace_access` rows in the canary cohort. Revoke affected connection rows and their OAuth grants.
- Verify new tool calls return no customer data, while normal API and web health checks still pass. Preserve audit and connection records according to the approved retention policy; do not drop the migration as a rollback shortcut.
- D1 revocation is the immediate access fence. Cloudflare KV is eventually consistent, so grant removal is not proof that every regional KV copy is erased instantly. Keep the 7-day grant lifetime and actual deletion verification in the privacy signoff; do not promise immediate physical erasure of all OAuth metadata.

## Evidence still required before customer access

- Reachable staging HTTPS origins, reviewed staging Worker configurations, dedicated KV/D1 resources, and dry-run binding evidence, with no production data exposed during setup.
- Review the local combined proof (`node scripts/validate-mcp-customer-chain-runtime.js`) and repeat it in the actual staging Worker configuration. The local fixture uses test-only entrypoints and a hostname shim; staging must prove the deployed bindings, cross-tenant denials, and revoked-token denial.
- Hands-on client checks for the exact Claude, OpenAI, and Gemini products to be advertised; Google consumer Gemini eligibility depends on Google's account and region rules.
- Customer-facing retention and third-party data-handling text, named pilot workspaces, operational monitoring, rollback exercise, and the Founder/Executive release decision.
