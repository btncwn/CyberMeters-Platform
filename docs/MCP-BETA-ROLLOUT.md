# CyberMeters MCP Beta rollout handoff

**State:** isolated staging is deployed with customer access disabled. The public staging MCP route returns `503 mcp_not_configured`; the staging API is in maintenance mode. Production MCP and customer access remain on hold. This document records staging preparation and the gates for a later named-customer rollout.

**Invited beta entitlement:** MCP access is enabled or paused per workspace in `mcp_beta_workspace_access`; an active invitation and a current Trial, Starter, Professional, Business, or MSP entitlement are required for each read. The MSP tier uses the platform's `enterprise` entitlement key. Single-workspace read is available on all five of those plans. Selected multi-workspace portfolio read requires Business or MSP and explicit workspace choices at consent; no workspace is selected by default. Trial is limited to 10 MCP reads per minute per connection/token, versus 30 for paid or grace access. When portfolio entitlement is lost, the portfolio connection and its grants are revoked; the user can reconnect with a new single-workspace consent if still eligible. A paused invitation, expired trial, deleted workspace, or revoked connection stops future reads. These are implementation rules, not a statement that customer access is already live.

## Release sequence

1. **Select the pilot.** Record the named workspaces, owner, support contact, supported client surfaces, and rollback operator. Check that every pilot user, including a single-domain legacy owner, has an explicit live `workspace_members` row; customer OAuth intentionally requires it. Approve the MCP audit retention and the customer notice about data handled by their chosen AI client. Keep the core product release decision independent of MCP.
2. **Prepare isolated staging.** Use the fixed `api-staging.cybermeters.com`, `app-staging.cybermeters.com`, and `mcp-staging.cybermeters.com/mcp` origins. Create and review separate staging Wrangler configurations for both Workers before any hosted test: the API route must target only the staging hostname, its D1 binding must use a dedicated staging database, its `OAUTH_KV` binding must use a dedicated namespace, and the gateway's named service bindings must target the staging API Worker. The checked-in production Wrangler files point at the production API route, D1, and service name; setting `MCP_DEPLOYMENT_TIER=staging` alone does not isolate them. Bootstrap a **new empty** staging D1 with the complete, locally validated platform schema through migration 124 using the procedure below; migration `121-mcp-oauth.sql` alone is insufficient because it references existing users, workspaces, and sessions. The already seeded staging D1 received migrations 122 and 123 separately; apply migration 124 there before a new hosted test, and never rerun the empty bootstrap on it. Dry-run both staging configurations to verify the effective routes and bindings. Set `MCP_DEPLOYMENT_TIER=staging` in both Workers. The optional `MCP_STAGING_*` assertions, if supplied, must match the fixed staging origins exactly. Keep staging data synthetic until the tenant and privacy gates pass.
3. **Configure the client boundary.** Keep the gateway's named `MCP_AUTH` and `MCP_CUSTOMER_BACKEND` service bindings and both edge rate bindings. Before customer beta, check whether the zone's one Free-plan WAF rate rule is already used. On Free, rate-rule matching can use the path but not the host, and counters are per IP with a 10-second window; scope any available rule to the exact OAuth/MCP paths without affecting unrelated paths. It only dampens per-IP bursts, so also prove a bounded distributed-request budget before customer access. The short synthetic hosted test used only staging data and the existing Worker rate bindings; it did not clear this customer gate. Configure exact hosted OAuth redirect URIs in `MCP_OAUTH_DCR_ALLOWED_REDIRECT_URIS` only for approved DCR clients and exact reviewed HTTPS metadata URLs in `MCP_OAUTH_CIMD_ALLOWED_CLIENT_IDS` for approved CIMD clients. Both default to `[]`; an empty CIMD list prevents the SDK from fetching an arbitrary client metadata URL. A Gemini Enterprise connection needs a separate operator-provisioned confidential OAuth client; never expose its secret in this repository or enable open confidential-client registration. See [Cloudflare's plan limits](https://developers.cloudflare.com/waf/rate-limiting-rules/#availability).
4. **Enable staging in order.** Deploy API and gateway code with customer flags absent; keep the staging API's `MAINTENANCE_MODE=on` and all MCP OAuth/read flags false. Only health and readiness routes should remain available at this stage; verify the gateway returns `503 mcp_not_configured`. For a short synthetic hosted test, keep maintenance on and use the separately validated staging-test configuration: its narrow `MCP_STAGING_AUTH_TEST_ENABLED` gate admits only staging password login, session read, and logout, while signup, scans, billing, and ordinary workspace routes stay closed. Enroll only the two synthetic staging workspaces in `mcp_beta_workspace_access` for that test. Enable `MCP_CUSTOMER_OAUTH_ENABLED`, `MCP_CUSTOMER_READ_ENABLED`, and `MCP_OAUTH_DCR_ENABLED` on the staging API and `MCP_CUSTOMER_ENABLED` on the staging gateway. Set `VITE_MCP_BETA_ENABLED=true` only on the staging app. Check OAuth metadata, PKCE consent, read-only tool discovery, tenant isolation, rate limiting, durable audit, revocation, account/workspace deletion fences, and an intentional audit-store outage. Immediately restore the disabled Worker configurations and pause the synthetic beta rows after the hosted test.
5. **Prove actual clients.** Test Claude Code, Codex CLI, and Gemini CLI with the customer OAuth flow. Test Claude.ai/Desktop, a private ChatGPT MCP app, and an eligible Gemini hosted surface separately over staging HTTPS before advertising each one. Record account/region/admin eligibility and an actual read, revoke, and reconnect for every advertised surface. A local protocol simulator is not a hosted-client pass.
6. **Decide the canary.** An explicit Founder/Executive beta decision is required before a production route, flag, or customer enrollment is enabled. Canary one named workspace, watch bounded success/denial/latency metrics and audit availability, then widen only after the evidence and support owner are recorded.

  VITE_MCP_BETA_ENABLED=true npm --prefix frontend run build

The preparation command requires `frontend/dist/_headers` to be an exact copy of tracked `frontend/public/_headers` and the built entry bundle to contain the exact staging API URL. ### Empty staging D1 bootstrap

The platform's `schema.sql` is a historical baseline. The effective schema is that baseline plus the migration chain; applying the raw files wholesale to a fresh D1 fails at known, exact historical overlaps. The generator uses the existing migration validator and its statement-level tolerance list to build one **empty final-schema** SQL file. It copies no production data and writes only to ignored `local/`:

```sh
node scripts/generate-mcp-staging-schema.js
```

Before any remote import, inspect the generated API Wrangler config and confirm its D1 UUID matches the dedicated `cybermeters-db-staging` database in Cloudflare. The read-only inventory of the newly created remote D1 returned exactly one non-`sqlite_%` object: Cloudflare's internal table `_cf_KV`; it contained no application tables. Repeat the query below immediately before import. Proceed only if its sole row is `type=table, name=_cf_KV`; stop on an application table or any other unexpected object. From the repository root, use the project-pinned Wrangler and the generated staging config; `--remote` is intentional and must never be changed to a production database name or config:

```sh
workers/scan-api/node_modules/.bin/wrangler d1 execute cybermeters-db-staging --remote \
  --config workers/scan-api/.wrangler/mcp-staging/wrangler.jsonc \
  --command "SELECT type, name FROM sqlite_master WHERE name NOT LIKE 'sqlite_%' ORDER BY name"
workers/scan-api/node_modules/.bin/wrangler d1 execute cybermeters-db-staging --remote \
  --config workers/scan-api/.wrangler/mcp-staging/wrangler.jsonc \
  --file local/mcp-staging-schema.sql
```

After import, read back `users`, `workspaces`, and `mcp_beta_workspace_access` counts (all must be zero), confirm `mcp_oauth_connections` exists, and run `PRAGMA quick_check` and `PRAGMA foreign_key_check`. Stop on any import or integrity error. Keep the generated SQL private in `local/`; it is an installation artifact for a **new empty staging D1**, not a routine migration or a production rollback method. See [Cloudflare's D1 execute command](https://developers.cloudflare.com/d1/wrangler-commands/#d1-execute) for `--file`, `--local`, and `--remote` behavior.

## Immediate rollback

- Disable the gateway's `MCP_CUSTOMER_ENABLED` flag or remove its public route; leave the rest of CyberMeters serving normally.
- Set `MCP_CUSTOMER_READ_ENABLED=false` on the API Worker and pause all `mcp_beta_workspace_access` rows in the canary cohort. Revoke affected connection rows and their OAuth grants.
- Verify new tool calls return no customer data, while normal API and web health checks still pass. Preserve audit and connection records according to the approved retention policy; do not drop the migration as a rollback shortcut.
- D1 revocation is the immediate access fence. Cloudflare KV is eventually consistent, so grant removal is not proof that every regional KV copy is erased instantly. Keep the 7-day grant lifetime and actual deletion verification in the privacy signoff; do not promise immediate physical erasure of all OAuth metadata.

Worker rate bindings, local outage tests, and the hosted audit rows do not replace these operational gates. Current emergency ceilings are `2/min` per IP and `8/min` global for authorize and token requests, and `2/hour` per IP and `12/hour` global for DCR. These are capacity limits, not a guarantee against distributed starvation or all D1 reads/writes under attack. Prove an API-side edge gate and observe actual D1 `rows_read`/`rows_written` before increasing limits or enabling customers. See [Cloudflare D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/) for the applicable account allowance.

Bounded 12-month `audit_events` and two-day MCP rate-counter cleanup passed local tests. Before production enablement, apply migrations 122–124 to production through the approved process, then verify scheduled execution, backlog alerts, grant and token purge, and the public Privacy Policy/DPA language in the deployed environment. MCP audit rows use the same table. Review the customer-facing third-party AI data-handling text, run a controlled content-rich scan/findings benchmark, name pilot workspaces, prove monitoring and rollback, and record the Founder/Executive customer-release decision.
