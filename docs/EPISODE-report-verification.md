# QUEUED EPISODE — Report Verification (tamper-evident Cyber MOT reports)

Status: **QUEUED — post-backlog / around M7 or first-paying-customer. NOT pre-beta, NOT a
launch-blocker, does NOT jump the frozen backlog (remaining items 6–18).** Captured 24 Jul 2026 from a
ChatGPT proposal + Claude adversarial/reuse review.

## The customer value (honest, sellable)
Canonical claim wording (method-accurate, ChatGPT-refined 24 Jul 2026):
> "CyberMeters records confirm that this report was generated by CyberMeters and that the
> submitted file matches the original report snapshot."

Nothing more. **Never claim "legally non-repudiable" / "qualified electronic signature"** —
technical integrity ≠ a legally-qualified e-signature. The wording states only the source +
integrity that is actually proven, and does not imply a certificate-based signature. This is
the anti-overclaim law ([[public-disclosure-minimisation]], verification-vocabulary).

## Reuse-first finding (evidence, 24 Jul 2026) — the hard part is ALREADY built
The M5.c reporting snapshot already binds report bytes to a **SHA-256 checksum** with an
**immutable per-attempt report ID** and **append-only** integrity:
- `remediation-registry.js:1441` — "the snapshot's own integrity is its SHA-256 checksum";
- `report-snapshot.js` engine (canonical JSON in R2, per-attempt key, D1 row bound to bytes);
- `crypto.subtle.digest("SHA-256")` already in use (`report-branding-v2.js:81`).

**What is genuinely missing = only the customer-facing verify SURFACE.** No report-
verification page/route exists today (all `/verify` routes are email/MFA/domain/cert). So
Phase 1 must be a **read surface over the existing snapshot checksum — NOT a new parallel
hash system** (reuse-before-creating; no second source of truth).

Canonical design chain (do NOT deviate):
```text
existing immutable report attempt → existing canonical SHA-256 checksum
  → public verification read-surface → QR / verification URL in the PDF
```
**Forbidden:** a second checksum table, an alternative report ID, or any parallel truth
source. The verify surface READS the snapshot's own checksum; it never mints its own.

## Phased plan (Claude-adjusted from the ChatGPT proposal)

### Phase 1 — SHA-256 verify surface (small, because the foundation exists)
- Public verify page (`verify.cybermeters.com/...` or an app route) + QR/URL stamped on the PDF.
- Upload-a-PDF or enter-a-report-ID → server recomputes/looks up the snapshot SHA-256 →
  returns produced-by-CyberMeters / unchanged-since-generation / generation timestamp /
  workspace+domain+assessment binding / audit event.
- Tenant isolation tests, deleted-workspace behaviour, public-verification PRIVACY rules
  (a public verify endpoint must not leak workspace/domain/assessment detail to an
  unauthenticated stranger — decide exactly what is public), rate limiting, mutation tests,
  live acceptance, legal wording review.
- **Canonical semantics to decide (not just "hash matched?"):**
  - re-rendering the same assessment → how is the NEW attempt shown vs the old one?
  - an old report: `invalid` or `authentic but superseded`? (an authentic older snapshot is
    NOT "fake"). States: `original / modified / superseded / unavailable`.
  - workspace deleted → does verification still resolve, and how much does it reveal?
  - public surface → minimum metadata that leaks NO customer/workspace/hidden-domain detail.
  - file upload → explicit guarantee the uploaded file is **hashed in-memory and NEVER
    stored** (compute SHA-256, compare, discard).
- **Item 6 prep = LAYOUT SPACE ONLY.** During item 6 (Executive PDF Content Depth), keep the
  renderer future-ready for a QR / short verify-URL / visible report ID — reserve the visual
  area only. Do **NOT** add a working verification URL, a "verified" claim, a dead link, or
  any copy implying the feature exists, while the real public endpoint is not built. The
  verify surface itself lands post-backlog.

### Phase 2 — KMS-backed platform signature — ARCHITECTURE DECISION (founder ADR required)
- Cloudflare has **no native HSM/KMS.** Options: Ed25519/ECDSA key in a Worker Secret (Worker
  can sign, but the key is readable in the isolate — NOT HSM-grade custody), or an external
  KMS (AWS/GCP) which **breaks Cloudflare-native architecture** + adds a dependency/latency/
  new trust boundary → needs an approved ADR.
- **Sharp caveat:** if verification is always "upload to verify.cybermeters.com", the
  server-side SHA-256 lookup is already sufficient. A signature only adds real value when
  verification must work **offline / by a third party without calling CyberMeters.** Do NOT
  build Phase 2 until that need is real. Adds: key ID/version, rotation, revoked/superseded
  report state, downloadable verification receipt.

### Phase 3 — PAdES / Adobe-trusted PDF signature / S/MIME — DEFER HARD
- Only if a regulated customer demands it. code/document-signing cert, byte-range signing,
  cert chain, OCSP/CRL, trusted timestamp authority, long-term validation, cert lifecycle,
  Adobe compatibility testing, legal wording. Certificate procurement + TSA + Adobe trust
  behaviour dominate the timeline, not the coding.

## Why queued, not now
Not in the frozen pre-beta backlog; not requested by any customer; not a launch-blocker for
the first two controlled invitations. It strengthens the "honest system-of-record" pillar and
is cheap because the foundation exists — which is exactly why it must not be allowed to jump
the remaining items 6–18. Schedule around M7 / first-paying-customer. See
[[pre-beta-execution-resequencing]], [[pre-invitation-strategic-review]].
