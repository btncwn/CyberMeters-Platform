# CyberMeters Finding Framework v1

**Sprint 8 — Trust & Methodology**
**Date:** June 2026
**Status:** Internal Reference — Not Customer-Facing

---

## Overview

This document catalogs every finding type currently generated by the CyberMeters scan engine. All data is sourced directly from `workers/scan-api/src/index.js`. No speculative findings are included.

Findings are produced by `computeScore()`, module-level intelligence functions, and the `buildEmailIntelFindings()` helper. Each finding has a canonical `id`, a source module, a severity level, a confidence level, and a score impact.

### 2.5 Brand Monitoring (`runTyposquatModule`)

No finding IDs are generated at the individual domain level. The module returns structured `domains[]` with:

- `risk_level`: high / medium / low
- `variant_type`: substitution / omission / duplication / transposition / hyphen_keyword / prefix_keyword

High-risk keywords: login, secure, account, verify, auth, portal, admin, support
Medium-risk keywords: help, service, online, my, app, customer, access, billing

DNS validation of candidates is deferred to the `/brand-monitoring/refresh` endpoint (separate subrequest budget). Findings are not DNS-confirmed at scan time.

## 5. Finding Quality Validation

Every finding that has `score_impact != 0` is expected to carry an `evidence` object validated by `validateFindingEvidence()`. The function checks:

- `evidence.source` is present
- `evidence.probe_target` or `evidence.target` or `evidence.queried_hostname` or `evidence.requested_url` is present
- `evidence.observed_value` or equivalent field is present
- `evidence.expected_value` is present (required when `score_impact != 0`)
- `evidence.manual_verification_command` is present
- `evidence.checked_at` timestamp is present

Quality levels returned: `excellent` (0 warnings), `good` (1–2 warnings), `partial` (3+ warnings), `missing` (no evidence object).
